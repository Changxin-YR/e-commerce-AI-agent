# 两篇论文的共同实验与证据协议

> V1.2 补充：未明确的评分分母、invalid_output、冻结门槛和模型支出以 `15_EVALUATION_FREEZE_CONTRACT.md` 为准。


版本：V1.1；2026-10-31（Asia/Shanghai）。

## 1. 目的与适用关系

本协议固定研究诚实性和可复现规则。具体业务标签、指标和数据口径以对应 SPEC 为准；有差异时先记录并统一后执行，不能默默选择有利口径。

研究结果目前全部为 `NOT_RUN`。表格模板中的空值不是零分、失败或已经产生的结果。

## 2. 正式实验前必须冻结的内容

每次实验版本保存 `eval/freeze_manifest.json`，包括：

- 研究问题、假设及能支持的结论范围。
- 数据集 ID、源文件/快照 SHA-256、获取时期、采样规则及随机种子。
- 开发集与测试集 ID 清单、分组规则及重复检查。
- 数据口径/ICP 的版本，标签定义和 unknown 规则。
- 模型供应商、精确模型 ID、可见版本、采样参数。
- B0/B1/B2 各方案的提示词哈希、工具集合、请求预算、重试与超时。
- 程序提交 SHA；没有 Git 时暂用代码归档哈希并说明。
- 评估器版本、gold 哈希、人工核验状态。
- 预先确定的指标、分母、排除规则和 K。

先生成清单再执行正式评估。不可在发现结果不利后修改口径，覆盖旧文件并声称同一次实验。

## 3. 数据划分

### 电商

建议 30 条开发任务、100 条测试任务。按问题类型、参数组合、复杂度分层；避免仅替换商品名的几乎相同模板充满两边。测试集含可以计算的问题、缺参数问题、无相应字段的问题和边界问题，各自单独报告。默认 90 条历史问数/澄清主集加 10 条故障注入稳健性集，主结果与故障结果分开。

如果研究的是同一历史数据库上的任务执行能力，数据库快照可相同，但测试问题和标准答案不可在调试中使用。若增加预测任务，则必须另行定义时间划分；本首版不包含销售预测。

### 获客

160 家企业的规划样本分为 40 家开发、120 家测试；同一企业、同一集团易混主体或同一官网域名不能跨集合泄漏。行业分层只用于候选构成，不是正确答案。正式抽样冻结后，官网采集失败的入选样本保留并记为证据不足，不作静默替换。只有预先定义且与预测无关的数据错误（例如同一 QID 重复）可按冻结规则处理，保留审计记录。不得因为模型预测困难而删除。

人工 gold 的标签schema允许 `match`、`non_match`、`insufficient_evidence`，并给出H1/H2判断、D1资料状态与证据。试验阶段验证三类存在可由人复核的情形；正式冻结样本可能缺类，应报告support=0并限定结论，不在看到预测后换样本凑类。使用固定快照判断，不要求标注者猜测企业当前预算或真实购买意图。

实体/集团分组隔离优先于精确样本配额；有偏差时报告实际数量，不为满足整数配额拆组。正式集抽样冻结前，12 家独立可行性样本须验证正例、反例和证据不足的定义确实可由人复核。

## 4. 比较方案和公平性

| 代号 | 电商 | 获客 |
|---|---|---|
| B0 | 确定性模板/手工查询基线，只在支持的任务集合内比较，并单独报告覆盖率 | 预先定义的关键词/业务规则基线 |
| B1 | 基础工具调用 Agent | 在相同证据材料和预算下直接进行模型判断 |
| B2 | 增加口径/结果核查与异常处理的流程 | 证据结构化、unknown 处理与复核路由的流程 |

主比较是同模型、同数据、同工具权限和预算下的 B1/B2。B0 的能力边界和覆盖率必须说明。若做消融实验，仅移除一个清楚定义的机制；作为可选分析，不强制增加多轮复杂实验。

获客固定候选集评估中关闭实时搜索，或对所有方案提供完全相同的冻结搜索/页面内容。不要让 B2 获得更多网站而 B1 只看公司名。独立的候选发现演示可以联网，但不能混入固定筛选指标。

## 5. 自动结果、人工结果与未知状态

保存模型输出类别与系统动作的两个字段。例如获客预测类别为 `match/non_match/insufficient_evidence`，系统动作是 `accept/reject/review_required`。模型输出的“证据不足”与系统主动交给人审核不能混为一类。

必报获客指标：完整三分类混淆矩阵和macro-F1、按D1资料可用性分层的结果与样本数；证据可判定子集上的二分类指标；自动处理覆盖率、复核率、过度断言和证据支持率。预定K的批次结果为可选附表。D1=HAS_USABLE_SNAPSHOT不代表H1/H2已经可判定；全量主表与有正文子集都保留。

`coverage = 自动 accept/reject 数 / 全部评估样本数`。不能用全量弃权获得看似完美的准确率。真实 gold 为证据不足但系统自动 accept/reject 时应记入对应错误，而不是事后从分母去掉。

可选批次 verified Precision@K 固定 K，并说明排序字段。V1.1默认仅按类别和company_id稳定排序，没有学习得到的类内优先级；报告并列组规模及次序影响，不以此证明细粒度获客优先级有效。推荐数少于 K 时报告缺额和实际推荐数，不能临时缩小 K；本方案默认缺额按未证实命中处理；其余具体排序与未知上界规则见获客 SPEC V1.1。Recall 仅指固定候选集内的匹配对象召回，不是整个市场客户召回。

人工修正后单独生成 `assisted` 结果，绝不覆盖 `automatic` 原始输出。人工耗时、完成数量和复核比例只能记录真实发生的事实。

## 6. 参考答案与评估器

电商主要数值通过独立 SQL/程序生成，和生产工具实现不共享同一个核心计算函数；对关键金额、订单去重、取消记录、完整期间等做实际人工抽查。金额统一使用原币种和预先规定的精度、容差。排序出现同分时，明确并列处理和次级排序。

获客 gold 由实际人员根据同一材料和标注规范确认。可先由模型提供建议，但需保留原建议与人审字段。至少争取独立人员复核一部分样本；无人复核时如实写成单人标注限制，不伪造 Cohen's kappa 或专家一致率。

LLM-as-judge 可辅助评价长文本，不能成为计算正确性、来源是否支持或人工标签的唯一依据。评价量表、检查样本和分歧处理需公开。

## 7. 运行与统计

每次运行保存 JSONL：项目、run_id、case_id、数据/标签版本、方案、模型配置、开始结束时间、输入、受限工具调用参数和结构化结果、输出、预期/预测、评估明细、重试、Token、延迟、费用口径、错误类型。

记录工具动作和简明决策依据，不要求保存或展示模型的私有思维链。密钥和敏感令牌必须脱敏。

建议主模型方案各重复 3 次，报告各次结果与按任务汇总的稳定性。100 道题重复 3 次仍是 100 个不同任务，不能当作 300 个独立任务进行统计推断。若做区间估计，按 case/company 为单位配对重采样，并说明方法；本科首版可以报告清晰的描述统计，不强制显著性检验。

每个 `case_id/company_id × variant × repeat` 使用独立会话与 thread，不继承上一题的对话、工具结果或人审记录。跨题只允许读取已冻结的公共数据快照；缓存策略、缓存命中及供应商可能的缓存计费均记录。不可让后一方案读取前一方案答案。

超时、接口错误、格式无法修复等没有有效预测的情况，保存 `predicted_class=null`、`run_status=FAIL` 和独立 `error_code`，不改写成业务上的“证据不足”。获客混淆表使用三个 gold 行、三个有效预测列加一列 `invalid_output`；计算三类 macro-F1 时，失败对真实类别计 FN，invalid_output 不作为第四个业务类别参与宏平均。各类 F1 使用 `2TP/(2TP+FP+FN)`，分母为 0 时置 0 并明确该类 support=0；同时报告实际类别分布。电商失败计入对应任务的未成功。全量端到端结果包含这些失败，可另附有效输出子集结果，但不得用子集替代主表。尚未尝试的任务单列 `NOT_RUN`；存在未运行项时不得宣称全测试集实验完成。

达到预算/超时或服务失败时保留失败记录。报告尝试数、完成数、失败数和未运行数，不悄悄去掉失败案例。供应商计费规则未核实则只报告 Token/次数和“货币成本未知”。

## 8. 论文结果生成

- `eval/raw/` 保存不可覆盖的逐次记录。
- `eval/results/` 保存机器生成汇总、指标定义与版本。
- `eval/figures/` 保存图表及生成脚本。
- `eval/error_analysis.md` 按真实失败类型总结代表性案例。
- `thesis/claim_evidence_map.csv` 把论文论点映射到表格、run_id、数据版本、代码或参考文献。

没有执行的实验在论文草稿中写“待执行”，不能用估计结果填图。公开演示中的缓存结果标明原运行日期和模型，不假装是当前实时生成。

## 9. 研究完成判据

正式实验完成要求：来源与样本可追溯、标签/标准答案状态清楚、方案和测试集冻结、实际运行记录完整、指标计算可复核、结论不超出设计边界。是否优于基线不属于通过条件。

模板缺失、标签缺失或 Key 缺失分别报告；不要把 `ENGINEERING_READY`、`DATA_READY` 和 `EVALUATION_COMPLETE` 混为一个绿色“完成”。

## 10. V1.1 实施约定

B1的电商实现为标准多轮工具循环，可读取结果与错误，具备正常的继续和结束能力。两组同schema、同数据、同工具与上限，公共基本类型/权限/引用合法性保持一致。B2差异是显式条件检查、跨结果与证据核查、有界业务修复。显式记录SDK、结构化输出和图重试配置，所有尝试纳入既有预算。人工等待时间与模型/工具运行时间分开。

获客H3不再是业务必要条件，D1采用三枚举并由身份/采集事实形成；H1/H2/A1仍用true/false/unknown。旧H3不能直接映射成D1；旧gold保留原ICP版本，V1.1需由真实人员确认，不自动标记新版本已审核。身份未确认时预测证据不足；字段冲突先转unknown，按必要条件真值表生成类别，但未解决冲突强制review_required。

正式计划B1/B2共1320次任务运行，是预期工作量而非已完成次数。真实模型开发冒烟、人工标注状态、调用上限与费用依据具备后再执行正式批量。09的月度参考属于开发对账材料，尚无真人抽查记录，不能视为已经完成正式gold人工核验。
