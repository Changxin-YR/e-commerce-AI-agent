## 1. 总体决定

两篇论文同时保留，分别开发为独立系统，不将它们合并成一个大平台。

| 项目 | 电商论文 | 获客论文 |
|---|---|---|
| 建议题目 | 基于 LangGraph 的电商经营数据分析智能体设计与实现 | 基于 LangGraph 的 B2B 客户线索研究与匹配智能体设计与实现 |
| 研究对象 | 有真实历史交易数据的小型线上零售业务 | 面向明确服务场景的企业级候选线索 |
| 主要问题 | 自然语言经营问题如何被正确转化为计算、核查和有依据的报告 | 企业资料如何被转化为可追溯、可复核的匹配判断 |
| 数据 | UCI Online Retail 真实历史交易明细 | Wikidata 企业种子及允许访问的企业官网证据 |
| 核心产出 | 可核对的指标、分析报告、执行记录 | 企业档案、证据、匹配状态、人工审核、跟进草稿 |
| 主要实验 | 数值正确率、任务完成率、无依据结论、成本 | 抽取正确性、分类、证据支持、覆盖率与成本；固定批次指标可选 |
| 开源参考 | LangGraph 官方实现；Shopify merchant 的工具与审批设计 | OpenOutFind 的发现/匹配拆分；Twenty 的对象与状态设计 |

本科工作量集中在业务建模、系统实现和对照实验。是否必须包含新算法、数学证明、指定中文文献或特定字数，以学院任务书为准；本方案不承诺任何学校的通过结果。

## 2. 两个系统的技术方案

默认技术栈：Python 3.11+、FastAPI、Pydantic、SQLAlchemy、SQLite；Vue 3、TypeScript、Vite；LangGraph、一个支持工具调用的模型；pytest、Vitest 和必要的 Playwright 端到端测试。

执行时核对当前兼容版本，使用锁文件固定实际安装版本。不要在文档中先编造某个未来版本。采用 HTTP API 形式接入模型，不要求训练、微调或本地部署大模型。

两个项目均采用单 Agent 加受限工具。数值计算、阈值判断、数据读写与最终规则执行交给确定性代码；模型负责理解任务、选择工具、抽取文本及组织说明。

SQLite 用于单机本科演示与实验。数据库连接保持可替换，不把 MySQL/PostgreSQL 迁移作为首版必做项。Redis、Celery、消息队列、向量数据库、多租户、移动端均不作为首版依赖。

前端提供清晰的业务页面和执行状态，不要求堆积仪表盘。接口错误、空数据、无模型密钥、处理失败均显示真实状态。

建议目录：

```text
graduation-theses/
  ecommerce-agent-thesis/
    backend/ frontend/ data/ eval/ docs/ thesis/ scripts/
  leadgen-agent-thesis/
    backend/ frontend/ data/ eval/ docs/ thesis/ scripts/
```

默认使用独立数据库文件、依赖锁文件和实验目录；需要同时启动时，电商前后端可使用 8000/5173，获客可使用 8001/5174，若冲突由脚本选择并记录实际端口。项目名称和端口只是默认值，可按现有工作区调整。

## 3. 电商论文的固定范围

### 3.1 业务主线

导入交易文件 → 生成数据质量报告 → 接收自然语言经营问题 → 检查时间和统计口径 → 选择分析工具 → 校验计算结果 → 生成带依据的报告 → 保存任务记录。

示例任务：比较 2011 年 9 月和 10 月的销售变化，列出下降贡献最大的商品，并说明数据能够支持的结论及仍需补充的信息。

### 3.2 必做功能

1. 真实数据导入与来源记录，保留原始文件及 SHA-256。
2. 对取消记录、负数、零价、缺失客户号、疑似重复与不完整时间区间进行明确处理。
3. 销售、订单、商品、地区与期间比较等受限查询工具。
4. 缺少条件时追问；没有相应数据时明确说明无法判断。
5. 数据表/图表、报告、查询依据、工具调用摘要及历史任务。

### 3.3 不纳入首版的范围

真实广告投放、自动改价、退款执行、库存补货、利润优化、客服平台、直播、支付、跨平台同步。源数据不包含这些能力需要的完整事实。

### 3.4 数据方案

主数据为 [UCI Online Retail](https://archive.ics.uci.edu/dataset/352/online+retail)，官方页面公布 541,909 条交易明细，期间为 2010-12-01 至 2011-12-09。下载后实际核对文件、工作表、字段和行数；网页元信息不能替代数据质量审计。

它属于历史经营数据。演示、图表和论文均明确标明数据时期，不称为今日实时店铺运营。价格单位为英镑，不能直接显示成人民币。取消记录不等同于已经验证原因的退货或退款。

### 3.5 主要研究问题

在相同模型、数据、工具权限及预算下，引入任务状态、结果校验和缺失信息处理，是否改善多步骤经营问题的完成质量？同时报告代价和失败情况。

## 4. 获客论文的固定范围

### 4.1 研究场景和默认 ICP

默认研究场景是假设一家团队提供“工业产品知识库与售前问答辅助服务”，希望优先研究适配该服务的工业设备/自动化硬件供应商。

默认画像以官网可核实的两项业务必要条件为主：

1. 公开可核实的供给包含工业设备或工业自动化硬件；不判断其收入占比或是否为最大业务。
2. 面向企业或其他组织客户，而非仅面向个人消费。
资料状态 D1 另存为 IDENTITY_UNCONFIRMED、NO_USABLE_SNAPSHOT 或 HAS_USABLE_SNAPSHOT；有可用正文不代表足以判断业务条件。H1/H2 为业务必要条件，身份与证据规则见获客 SPEC V1.1。

询价、销售联系入口等作为补充信息。企业规模、预算、决策人、采购计划与真实购买意向没有证据时保持未知。该画像是本研究预设的业务适配假设，不代表某家真实服务商已经验证的市场需求。

### 4.2 业务主线

配置画像 → 从公开目录发现/导入候选企业 → 核对官网身份 → 获取有限业务页面 → 保存证据 → 抽取事实 → 去重与匹配 → 输出符合/不符合/证据不足 → 人工复核 → 生成待审跟进草稿。

### 4.3 数据取得

无付费主线采用 [Wikidata 的 CC0 结构化企业数据](https://www.wikidata.org/wiki/Wikidata:Licensing)及官网地址作为种子，随后核查官网。Wikidata 的行业字段只用于候选构建和分层抽样，不作为目标客户真值。官网地址可能过时，不能看到 P856 就视为当前官方网站。

计划构建 160 家真实企业的分层样本：工业相关 80，软件/专业服务 40，消费/零售及其他 40。先冻结候选池、抽样规则和随机种子，再人工标注；不可看匹配结果后替换难例。建议 40 家开发集、120 家测试集，按公司实体/域名分组，避免同一家公司进入两边。具体分配和不足样本处理以项目详细规格为准。

每家最多采集 3—5 个必要公开业务页面。页面无法访问、禁止采集、需要登录或身份不确定时保留失败与未知状态；不绕过登录、验证码或访问控制。原始网页材料仅在许可允许范围内保存和使用，公开交付以来源、结构化事实、必要短证据和摘要为主。

搜索 API 或 BetterContact 可作为有账号时的扩展，不是首版成功的前提。

### 4.4 主要研究问题

相较关键词规则和直接模型判断，证据约束、明确未知状态及复核路由能否改善企业匹配的可靠性？这种改善付出了多少额外调用和人工复核成本？

固定候选集上的筛选实验不证明全网客户发现效果。匹配符合度不证明购买意向，更不证明回复率、成交率或营收提升。

## 6. 阶段安排与交付门槛

| 阶段 | 必须交付 | 进入下一阶段的依据 |
|---|---|---|
| M0 范围与环境 | 环境报告、范围文件、复用清单、风险和阻碍记录 | 项目能安装最小依赖，默认决策已记录 |
| M1 数据试跑 | 电商真实文件审计；获客先 12 家独立样本的官网试采集 | 来源能追溯，字段/证据可读取，缺项不伪造 |
| M2 业务核心 | 数据模型、工具、接口、关键确定性测试 | 核心业务结果可独立核对 |
| M3 最小前端 | 五个左右业务页面、错误/空状态、真实数据展示 | 用户能走完核心流程 |
| M4 Agent 闭环 | 真实模型调用、澄清/异常路径、任务记录 | 在开发集上执行并保存真实日志 |
| M5 实验 | 冻结清单、运行原始数据、结果表、失败分析 | 标签/答案已核验，实验记录可重跑 |

可并行：两个项目的 M0—M3、获客人工标注准备、电商参考答案整理。依赖模型、人工或模板的部分单独阻断，不将全项目停在空白计划。

在没有已确认截止日期时，按个人开发约 6—8 周作为排期占位：第 1 周范围/真实数据试跑；第 2—3 周核心与界面；第 4 周 Agent 和数据冻结；第 5 周实验；第 6 周论文草稿与复现；其余时间用于人工核验、修复和学院格式。此时间是计划估算，不是进度事实或工期承诺；实际根据首次环境/数据报告调整。

## 7. 验收分成工程、数据、研究三层

### 7.1 工程验收

安装与启动说明可执行；核心接口、页面和受限工具有效；失败有明确状态；两项目不串库；不泄露密钥；测试与演示有日志和截图。无明显阻断性缺陷，已知问题明确披露。

### 7.2 数据验收

电商下载来源、哈希、清洗数量、日期覆盖和口径可追溯。获客公司、官网身份、页面时间、证据与人工标签可追溯。没有真实数据时不得用随机业务数据填满界面后宣称接入完成。

### 7.3 研究验收

实验方案事先固定，基线公平，开发/测试分离，结果按真实运行生成，失败和不利结果保留。准确率提升不是必须出现的验收条件；“测试真实执行、指标定义正确、结果可复核”才是要求。

只有人类标注者才能确认人工标签。模型可以提供候选标注供审核，不能冒充人类填写审核者、时间或一致率。没有标签时交付标注包，并将相应实验标为 `ANNOTATION_REQUIRED`。

## 8. 论文组织

每篇建议六章：绪论；相关研究与技术；需求及系统设计；关键方法与实现；实验与系统测试；总结与不足。实际篇幅与格式根据学院要求调整。

电商第 4—5 章重点是交易口径、工具契约、跨步骤核验与问数实验。获客第 4—5 章重点是企业实体、证据结构、匹配/未知状态、D1资料分层、标注与分类实验。两篇分别展示自己的数据库图、流程图、页面、结果和失败案例。

先写可确认的需求与方法部分；结果章节等待实际实验。未得到的数字写为待测字段，不能预先填写“准确率 95%”“提高 30%”等。

## 10. 两篇的实验预设

下表是待执行的设计，不是已经取得的数据或结果。

| 项目 | 电商 | 获客 |
|---|---|---|
| 开发材料 | 30 条开发任务 | 独立 12 家可行性试验；正式集内 40 家开发企业 |
| 测试材料 | 100 条任务：90 条历史问数/澄清主集，10 条故障注入稳健性集 | 计划 120 家测试企业，三类标签可用；实际缺类则报告support=0，不后验补换 |
| 真值 | 独立 SQL/Decimal 计算与真实人员抽查 | 人类按冻结官网资料标注；第二人尽量独立复核至少 30 家 |
| 对比 | B0 模板、B1 基础 Agent、B2 加核验与恢复 | B0 规则、B1 直接模型判断、B2 证据约束流程 |
| 重复 | B1/B2 各 3 次；B0 确定性部分一次 | B1/B2 各 3 次；B0 一次 |
| 首要指标 | 数值正确率、任务成功率、澄清/不足处理与成本 | 全量三分类 macro-F1、D1分层、覆盖率、过度断言、证据支持与成本；固定批次@K可选 |
| 失效情况 | 工具错误、模型超时计任务失败；主集与故障集分报 | 无有效预测计端到端失败；采集资料不足与推理报错分开 |

获客的公司/集团分组隔离优先于精确 40/120 配额，有偏差如实报告。12 家可行性试验必须验证正例、反例和证据不足的定义可以实际标注；需要改规则时在正式样本冻结前完成。仅为软件测试构造的企业与交易行不能替代真实研究材料。

两篇都不需要训练大模型。研究着重验证具体流程是否可靠，以及为此增加了多少时间、模型调用和人工复核成本。效果持平或变差仍然可以构成真实的实验结果，论文应分析原因和适用边界。

## 11. 如何交给 Codex

1. 解压执行包，分别准备 `ecommerce-agent-thesis` 与 `leadgen-agent-thesis` 两个项目目录。
2. 每个项目将完整执行包放入 `docs/plan/`，或通过 Codex 会话附件提供。现有项目先保留原文件。
3. 在本项目根目录内开启 Codex 会话，完整粘贴 `CODEX_START.md`。完整指令已包含读哪些文件、从哪一步启动和怎么继续执行。
4. 先读取 `08_REVIEW_AND_CHANGES.md`、`10_RUNTIME_CONTRACT.md` 与 `11_FIRST_SLICES.md`及 `09_DATA_PREFLIGHT.md`；首轮按11规定的电商真实查询和获客证据档案流程贯通，再逐步补齐最终范围。两个会话可以并行，但各自只改自己的项目。
5. 真实调用模型时，在本地配置已授权的模型 Key；人工标注由真实人员完成。暂缺时 Codex 先交付具体配置模板/标注材料并继续其他工作。
6. 若会话中断，新会话先读 `docs/NEXT_SESSION.md` 与实际状态，不重新创建已经存在的工程。

后续需要用户提供的具体输入只有：实际学院任务书与模板、可用的模型配置及预算、真实人工核验。截止日期和已有代码路径若有也可一并提供。这些信息影响对应阶段，不阻止现在开始环境、数据和业务核心开发。
