## 1. 审查结论

两篇题目和技术路线可以继续执行。电商聚焦历史交易分析，获客聚焦企业线索研究与条件匹配；FastAPI、Vue、SQLite与LangGraph足以承担当前本地开发范围。没有必要为开工新增完整CRM、多智能体、向量数据库或云端任务集群。

原V1.0的详细规格已经覆盖真实数据与测试夹具分离、金额精度、取消与退款区分、未知与失败分离、盲标、实验冻结、B0适用范围、累计预算及不利结果保留。本次完整读取原执行包后保留这些规则，不将已写明内容重复包装成缺陷。

V1.1主要解决三个问题：把数据要求落到实际原文件；修正获客画像和排序的语义；将任务恢复与第一轮开发顺序写成可以执行、可以检查的要求。

## 3. 需要落实的优化

### 3.1 电商：从“金额精确”落实到原文件规范化

实测原文件有135,080行CustomerID缺失、1,454行Description缺失、4行单价为0.001 GBP，以及运费、银行费用等条目。详见09及实际JSON。由此确定：普通金额分析不能因客户编号缺失而丢行；单价不能强制存整数便士；默认金额是带明确纳入规则的交易行金额。

原XLSX还存在Excel表示尾差。本次逐行核验发现所有价格与0.001 GBP网格之间的差不超过7E-13 GBP。V1.1对这份固定哈希文件采用“差值≤1E-9时消除表示尾差，再存整数千分英镑”的规则，同时保留原始表示。其他上传文件重新审计，不自动采用这项规则。

行分类需要区分互斥主分类和可重叠质量标签。比如非C负数量与零价格会重叠；若直接相加会把排除记录重复计数。商品/费用分类同样不能仅靠StockCode是否为数字决定。

### 3.2 电商：报告数字必须能定位到工具字段

为关键主张保存claim_id、tool_call_id、field_path、指标/数据版本、期间和过滤器。程序从对应结果解析精确值及单位，模型组织说明。基础引用合法性由B1/B2共同具备，B2增加任务覆盖、跨结果对账和业务一致性检查。

变化拆解采用两期间条目并集，新项和消失项补零，Top K外保留其他项。差额可能互相抵消，因此贡献比例可为负或超过100%；总差额为零时比例为空。不要为了图表好看强制压在0—100%。

### 3.3 获客：业务条件与资料状态分别定义

H1明确为“公开供给包含工业设备或工业自动化硬件”，H2为“面向组织客户”。去掉无法普遍从现有字段验证的“主营收入占比”含义：经销商可以供应硬件，兼容某硬件的软件企业不因此被视为供应该硬件。

旧H3移为D1：身份未确认、没有可用快照、有可用快照。D1表示资料状态，不给业务加分，也不保证正文足以判断H1/H2。主结果保留全部候选，再附有可用正文子集结果，分开解释采集可用性与业务判断能力。

身份不明时不用该站材料作企业结论；同字段仍有实质矛盾时置unknown并保存证据；按必要条件真值表生成类别，但任何未解决冲突强制转人工。可靠false仍可产生non_match，不能取消冲突复核。

H3到D1属于画像版本变更，旧gold必须保留旧版本，新版人工确认真实发生后才可作为新gold。不能改一个字段名就声称人工审核仍然有效。

### 3.4 获客：去掉没有足够解释力的默认加权分数

V1.0的公式为35H1+35H2+20H3+10A1，而match已经要求H1/H2/H3全真。因此同为match的企业主要只因A1（咨询入口）而形成90或100的分数，随后大量并列由company_id决定。这是根据原公式推导的设计问题，与模型实测准确率无关。

V1.1默认展示类别、逐项依据、未知和复核状态，不再强调百分制分数。主指标保留分类、自动处理覆盖、过度断言、证据支持和成本。固定批次@K作为可选附表，披露同类稳定次序及并列规模，不据此主张细粒度客户优先级有效。

正式分层随机样本可能没有某一gold类别；如实报告support=0并限制结论，不能在看到预测后换样本补齐。试验阶段仍需确认三类定义均有可由人复核的真实情形。

### 3.5 两篇共同：补全运行恢复契约

业务任务表与LangGraph checkpoint分别负责任务记录和执行状态，通过run_id/thread_id关联。进程重启后原执行中任务转为中断，等待补充条件的任务保留；恢复前检查状态、版本和已耗预算。重复恢复不重复保存报告或复核记录。查看历史只读取已保存结果；重新运行另建记录。

LangGraph官方说明中断恢复会从所在节点开头重新执行；内存checkpointer不能跨进程重启保留。因此10的幂等与持久化要求直接影响实际实现，而不只是文字规范。[来源见第7节]

### 3.6 两篇共同：把B1和隐藏重试写清楚

电商B1应是可正常多轮调用工具、读取结果和错误、继续或结束的标准循环。两组可以都用LangGraph，比较增强流程组合，不将任何提升笼统归因于框架。

原方案已经要求全部重试计入预算。V1.1进一步要求显式配置SDK、结构化输出和图节点重试，统一记录每次尝试；框架默认修复不能藏在统计之外。模型调用已发送却因进程退出无法确认响应时，记录UNKNOWN_OUTCOME并保守占用额度，不按零成本处理。

### 3.7 开发顺序：先得到可运行结果

首轮顺序改为11规定的E-S1/L-S1：电商真实导入、一个月份查询和结果页；获客少量企业的来源、证据、详情和标注保存，再扩展12家。随后接入真实模型、恢复机制和完整范围。原五/六页面、八工具仍是最终功能范围，不要求第一轮一次写完。

正式模型计划合计1320次任务运行，每个任务可能包含多次模型调用。先跑少量开发样本记录真实成本和耗时，再确定完整预算和工期；6—8周继续只是占位估算。
