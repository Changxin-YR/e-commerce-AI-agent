## 1. 固定题目、目标与完成边界

**推荐题目：《基于 LangGraph 的电商经营数据分析智能体设计与实现》。**

研究对象为电商历史交易记录上的经营查询与分析。系统帮助使用者用自然语言完成指标查询、商品或地区比较、期间变化拆解，并给出能追溯到数据与计算过程的报告。

核心研究问题：在相同模型、数据和工具条件下，加入任务状态管理、参数校验、结果核验及异常处理，是否能提高经营分析任务完成质量，以及带来多少耗时与调用成本。

论文结论限定在离线历史数据上的查询正确性、任务完成质量和运行成本。销售变化只做可计算的构成拆解；缺少活动、流量、竞争或访谈资料时，不能宣称发现商业因果。系统运行成功不能替代实验证据。

一期必做：数据导入与质量报告、确定性指标计算、受限工具调用、单智能体分析流程、带依据的报告、任务日志与实验复现。暂不纳入广告投放、利润优化、自动定价、退款执行、补货预测、实时平台同步、完整 ERP、多租户或多个专业智能体。

学院任务书、导师确认后的题目、模板和学术要求优先。缺少这些材料时先把系统及实验基础做完，把论文格式标为 `SCHOOL_TEMPLATE_PENDING`，不虚构已经通过导师或学院审核。

## 2. 实施原则与开源使用方式

沿用熟悉的 Python/FastAPI 与 Vue 技术栈，使用 LangGraph 编排流程。LangGraph 官方文档说明其可以组合确定性步骤与模型驱动步骤，适合本项目的“精确计算＋自然语言调度”设计。[S2]

若已有 SoloOps 等电商代码，Codex 先检查当前明确提供的工作区、README、依赖与可运行情况，形成复用清单。只复用与本题有关且能够解释的模块，保持原项目数据和代码完整；发现路径不明确时新建独立项目，不猜测其他磁盘上的仓库位置。

Shopify `merchant` 示例只用于理解工具接口、数据读取与执行边界，记录阅读或复制的确切文件、提交版本及许可证。该示例不带商家 Web UI，不能假定复制后就得到完整系统。[S3] 本题不整套引入 Enthusiast、Ignitic 或完整电商后台，也不要求 Shopify 账号。

凡直接使用开源代码，填写 `docs/reuse-register.md`：来源 URL、commit、许可证、复用文件、原有功能、本人修改和新增部分。框架本身、现有算法与他人代码不写为原创成果。

## 3. 数据方案：真实历史交易数据

### 3.1 主数据源与保存规则

主数据集选用 UCI Online Retail，官方页面列示 541,909 条交易明细，时间范围为 2010-12-01 至 2011-12-09，字段包括发票编号、商品编号、描述、数量、交易时间、单价、客户编号和国家，单价币种为英镑，许可为 CC BY 4.0。[S1] 这些是交易明细条数，不能写成同等数量的订单。

执行时从官方页面解析下载入口，不使用随意找到的二次加工版本。下载后记录实际文件名、URL、下载时间、字节数、SHA-256、工作表、实际行数、字段类型、时间边界及许可说明。原始文件放入只追加的 `data/raw/`，清洗结果另存；原始文件不得被覆盖。

`data/manifest.json` 至少含 `dataset_id`、`source_kind=real_historical`、`source_url`、`doi`、`downloaded_at`、`sha256`、`row_count`、`time_min`、`time_max`、`license`、`transform_version`、`metric_version`。界面、导出报告和论文都显示“真实公开历史交易数据”，不得展示成当前生产店铺的数据。

如果官网说明与实际文件不一致，以实测结果和保留的来源记录说明差异；不要因网页写“无缺失”就跳过逐列检查。若下载失败，可继续开发导入器、测试与界面，但将真实数据验收标为 `status=BLOCKED, blocker_code=SOURCE_UNAVAILABLE`。小型人工构造 fixture 仅用于单元测试，必须标记 `test_fixture` 并与论文实证数据隔离。

### 3.2 必须冻结的数据处理口径

| 情况 | 处理约定 |
| --- | --- |
| InvoiceNo 以 C/c 开头 | 标记取消类记录；不直接推断退款原因、退货原因或退款已完成 |
| 普通销售记录 | 发票号非 C 开头、数量大于 0、单价大于 0，并通过关键字段校验 |
| 取消类且数量小于 0、单价大于 0 | 单独计入取消类金额；可按冻结口径纳入净交易金额 |
| 非 C 单负数量、C 单正数量、负单价 | 标为冲突或调整类待检查；默认不进入主销售指标，报告排除数量与金额影响 |
| 数量为 0 或单价为 0 | 保留原始记录；主有价销售指标排除，质量报告单独统计 |
| CustomerID 缺失 | 可进入不依赖客户身份的销售统计；从客户去重或复购等指标排除，并明确分母 |
| 商品描述缺失 | 保留商品编号；不能让模型补写一个“真实描述” |
| 完全相同行 | 默认保留并标记；相同交易行可能是真实多次录入，不能无依据直接去重 |
| 同一文件重复上传 | 按文件哈希幂等复用同一导入批次，避免重复导入造成翻倍 |
| 日期与时区 | 源文件无明确时区时记录 `source_local_unspecified`；不擅自当 UTC 转换 |
| 月份不完整 | 明确标记覆盖范围；2011 年 12 月数据不能直接与完整 11 月作完整月环比 |
| 基期为 0 | 增长率返回 `null` 和原因，展示新增/无可比基数，不能除零或显示无限增长 |

自动剔除只作用于派生视图，必须保留行级原因；对所有输入行给出可核对的分类数量。异常规则和可能的特殊商品编码须先分析后记入数据字典，不根据名称随意删除运费、折扣等记录。

### 3.3 固定指标

一期指标：

1. **正向交易行金额（销售研究口径）**：符合普通销售条件的 `Quantity × UnitPrice` 之和。
2. **取消类金额**：符合取消口径的金额绝对值之和；命名不能直接替换为“实际退款金额”。
3. **净交易金额（研究口径）**：正向销售金额减取消类金额，明确它不是经财务确认的营业收入。
4. **有效订单数**：普通销售条件下的不同发票编号数；先检查一张发票的国家、客户、日期一致性。
5. **商品/国家排名及占比**：仅按前述指定指标排序，缺失地区进入“未知”分类并显示。
6. **期间差额与构成贡献**：`本期金额－基期金额`，按商品/国家拆解后应与总体差额一致。

金额采用 Decimal 或无损定点数，禁止直接用二进制浮点结果作为精确金额真值。导入时检查原始单价小数位；选定的存储精度必须覆盖实际输入，超出时报告而非静默舍入。统一在展示层按明确规则四舍五入至两位，测试以未舍入精确值与展示值分别核验。SQLite 的通用 NUMERIC 聚合若会转成浮点，应改为定点整数聚合或 Decimal 服务计算。

“交易记录显示的金额变化”与“商业经营原因”分开表达。缺少成本、广告费用、浏览量和库存，工具必须返回 `UNSUPPORTED_METRIC`，不猜测利润、转化率、ROAS 或缺货量。

## 4. 系统设计

### 4.1 技术与部署

- 后端：Python、FastAPI、Pydantic、SQLAlchemy、Alembic、LangGraph；数据计算用 SQL/Decimal，文件解析用适合 XLSX/CSV 的库。
- 前端：Vue 3、TypeScript、Vite；表格和少量趋势/构成图即可，组件库由执行时选择一个并锁定。
- 数据库：SQLite 为默认开发与答辩环境，通过仓储层保持未来迁移能力。单用户本地模式，不建设完整 RBAC。
- 模型：一个可配置、支持工具调用的模型；通过用户自有 Key 调用。执行时核实可用接口、准确模型名和 SDK 版本，并记录模型配置。
- 运行：默认只监听 localhost；建议后端端口 8000、前端 5173，避免与获客系统冲突。需要公开部署时另行完善认证，不默认公开上传接口。
- 版本：先记录操作系统与已安装 Python/Node，再选择相容版本并写入 lockfile。文档不能以无固定版本的 `latest` 作为复现实验环境。

本地演示无需 Redis、Celery、向量数据库或 Kubernetes。不要为使用 RAG 或多智能体而额外加入无明确用途的模块。

### 4.2 五个页面

| 页面 | 必须展示 |
| --- | --- |
| 数据集与导入 | 来源、时间、哈希、导入状态、重复文件提示、原始/有效/排除行数 |
| 经营概览 | 固定口径指标、日期选择、商品/国家分布、不完整期间提示 |
| 智能分析 | 用户问题、追问、执行阶段、工具结果摘要、结构化结论 |
| 报告详情 | 指标版本、数据快照、过滤条件、证据项、无法判断的事项、导出 |
| 任务与实验 | 运行状态、耗时、调用次数、失败原因、实验版本与结果链接 |

页面应包含空数据、导入失败、模型未配置、运行超时和部分成功等状态。主要验证桌面浏览器，核心表格可横向滚动；不额外承诺移动 App。

### 4.3 数据实体与 API 范围

实体最少包括：`DatasetSnapshot`、`ImportBatch`、`TransactionRow`、`QualityIssue`、`AnalysisRun`、`ToolCall`、`Report`、`ExperimentCase`、`ExperimentRun`、`ReviewRecord`。

关键关联为：数据快照绑定导入批次及原始行；任务绑定数据快照和指标版本；工具调用绑定任务和参数；报告引用工具结果 ID；实验运行绑定冻结用例集与代码提交。所有状态变化保留时间和错误码。

API 分为 datasets/imports、metrics、analysis/runs、reports、experiments。通过 OpenAPI 暴露契约。分析接口支持创建任务、查询状态和补充澄清；SSE 可用于阶段与结果流，但断线后应能够按 run_id 查询结果，不能把浏览器长连接当唯一任务状态。

### 4.4 八个白名单工具

| 工具 | 输入要点 | 输出要点 |
| --- | --- | --- |
| `get_dataset_profile` | dataset_id | 时间范围、字段、币种、数据类型、可用指标 |
| `get_metric_definitions` | metric_names | 指标公式、纳入排除规则、版本 |
| `get_quality_summary` | dataset_id、可选日期 | 缺失、异常、重复候选、期间覆盖 |
| `query_metric_series` | metric、日期、粒度、受限过滤器 | 序列、精确值、有效行数、口径 |
| `rank_entities` | metric、product/country、日期、top_k | 排名、总量、其他项、并列规则 |
| `compare_periods` | metric、两个区间、过滤器 | 差额、增长率或无基数原因、可比性 |
| `decompose_change` | metric、product/country、两个区间 | 各实体差额、贡献及对账结果 |
| `inspect_transactions` | 已验证过滤器、limit≤50 | 受限明细、总命中数、字段含义 |

工具以 Pydantic/JSON Schema 校验。过滤字段、比较操作、日期格式、排序项和 `top_k` 均受限；数据库连接和任意 SQL 不交给模型。统一返回 `status`、`data`、`evidence`、`warnings`、`error`。证据至少含 dataset_id/hash、metric_version、时间区间、filters、查询或计算标识、匹配行数、排除概况。

工具负责强制只读和资源上限，不能依赖提示词约束权限。文件导出由系统固定流程执行；模型不能指定任意磁盘路径、shell 命令或外部发送地址。

### 4.5 LangGraph 流程与状态

流程节点为：接收问题、读取数据上下文、解析条件、判断是否追问、计划工具调用、执行工具、校验结果、必要时有限修正、整理报告、结束。

状态保存 `question`、`dataset_id`、`time_range`、`filters`、`planned_steps`、`tool_results`、`validation_errors`、`clarification`、`budget`、`report_id`。模型可以根据任务选择多个工具，但不得超出工具白名单与预算。

缺少时间、指标含义不清或“本月”超出历史数据范围时先追问；不得默默把当前年月改成历史年月。用户明确允许采用默认区间时，报告必须显示这个区间。输入要求利润、实时库存等不存在的数据时给出证据不足原因。

结果校验至少包括：参数合法、查询非意外空集、期间覆盖、数值精度、排名合计/差额拆解对账、引用可解析，以及最终文本中关键数字与工具结果一致。只比较字符串或让另一个 LLM 自评分不够。对无法机械校验的解释，保留人工复核项。

默认预算建议：每任务最多 12 次工具调用、8 次模型调用、同一格式/工具错误最多修正 2 次。达到上限输出部分结果和未完成原因。模型预算涵盖全部节点、工具内部调用和重试；不以隐藏嵌套调用绕过上限。网络瞬时失败可有限重试；重复调用不无限循环。预算参数须写入配置，实验各方案保持一致。

## 5. 实验设计与论文证据

### 5.1 三组方案及比较边界

| 组别 | 方案 | 用途 |
| --- | --- | --- |
| B0 | 固定筛选表单＋确定性模板报表 | 统计已支持场景的正确性、覆盖范围和操作成本；不与开放任务直接混算准确率 |
| B1 | 同模型、同工具的标准多轮工具调用循环，正常读取工具结果和错误再继续 | 主要基线，保留相同只读权限和资源上限 |
| B2 | LangGraph 编排＋结果校验＋澄清/有限恢复 | 本文实现方案 |

论文主要比较 B1 与 B2。B0 只在共同可处理的任务上做对照，其范围外任务标 `not_applicable`，不能通过给 B0 大量不适用任务人为制造优势。B1 与 B2 均可由LangGraph承载，B1不是仅调用一次的简化桩。两组采用相同输出schema与基础引用合法性检查。B1 与 B2 的模型、温度、数据快照、工具、最大预算、输入题目保持相同；B2 新增校验调用的实际成本计入结果。只读权限、参数类型校验和基本资源限制是各方案共同的工程底线；B2 的差异是任务条件检查、跨工具对账、最终数字核验和有限恢复。该比较评价整个流程组合，不单凭总体结果宣称某一个机制具有独立因果效果。

### 5.2 用例与标准答案

建议先做 30 条开发用例，再独立建立 100 条测试用例：25 条基础指标、20 条多条件筛选、20 条多步骤对比/拆解、15 条缺参或超出时间范围、10 条数据不支持的问题、10 条受控异常或工具故障。分类可以在冻结前调整，但必须记录理由。

按问题模板、实体和日期组合检查重复，避免把开发题轻微改写后放进测试集。测试题包含可以回答和必须澄清/说明不足的情况。受控工具故障属于明确标注的工程测试，不能混称真实商业事件。100 条测试任务中，前 90 条构成历史数据问数/澄清主集，后 10 条构成故障注入稳健性集。分别报告 90 条主集和 10 条稳健性集的结果；若附全部 100 条加权结果，明确构成与权重，不能将受控故障描述成真实店铺事件。

标准答案由独立 SQL/Decimal 参考计算和预先定义的状态要求生成；避免直接调用待测工具得到“标准答案”。保存参考脚本、过滤参数、未舍入结果和解释规则。由真实人员复核至少 20% 的样本及所有有争议的口径；这项工作标 `ANNOTATION_REQUIRED`，Codex 可以生成复核表，但不得冒充本人、同学或导师签名完成复核。

澄清题默认只评价首轮：用例写明 `expected_action=clarify`、必需追问字段和不可擅自采用的默认值；正确追问即可满足该题要求，不无限等待真人输入。如果另设“澄清后完成分析”用例，必须预先保存固定用户答复脚本，两方案收到相同答复并按最大轮数运行。超出字段能力的问题设 `expected_action=unsupported`。每题验收依据在测试冻结前写清。

冻结文件至少包括：`dev.jsonl`、`test.jsonl`、`reference_answers.jsonl`、`rubric.md`、`freeze_manifest.json`。清单记录数据哈希、用例哈希、指标版本、提示词版本、代码 commit 和冻结时间。开发阶段只使用 dev；首次查看 test 结果后不能继续针对同一测试集调参，再将其当未见测试集报告。修复真实程序错误时保留旧结果，记录变更并使用新冻结版本，必要时新建保留测试集。

### 5.3 指标与重复运行

- 数值正确率＝关键数值均符合预设容差的可回答任务数／可回答任务总数。金额、比例、排名各有独立容差与并列规则。
- 完整任务成功率＝完成该题全部必需条件的任务数／任务总数；各类任务分别报告。
- 澄清/不足处理正确率＝正确触发并说明原因的相关任务数／该类任务数。
- 无依据结论比例＝经规则及人工核查发现无证据的事实性结论数／被核查的事实性结论总数；注明抽样方法及样本数。
- 工具与系统指标＝工具失败率、修正次数、预算耗尽率、运行耗时中位数/P95、模型调用次数、token 使用量和实际可确认费用。

主实验每个模型方案对同一测试集运行 3 次，保留全部结果与固定种子（供应商支持时）。温度为 0 也不能声明绝对确定。以同一 case_id 配对比较 B1/B2，报告各次结果和跨次均值；可对任务维度做配对 bootstrap 区间，但不得把同一任务的 3 次调用当 3 个独立业务样本夸大显著性。

真实费用无法从供应商得到时，只报告 token 和“费用未核实”；需要估算时注明模型价格来源、核验日期、币种与估算公式。无模型 Key 时只完成 B0、工具与流程测试，B1/B2 标 `BLOCKED_CREDENTIALS`，不生成虚假的实验成绩。

### 5.4 工程验收与研究结果分开

工程硬门槛：数据文件可核对；清洗有说明；冻结指标的人工边界样例全部通过；工具只读；越权参数被拒绝；模型不可用时不伪装成功；同一输入与同一快照的确定性工具结果一致；任务与报告可追溯；五页面核心流程实际执行通过。

模型准确率、任务成功率和改进幅度属于实验结果，不能预写为必须达到 95% 或必须优于 B1。若 B2 没有提升，也应保留真实结果，分析校验成本、错误类型和适用条件。不得删去失败样本、只保留最好一轮或声称“达到生产级”。

### 价格与行分类

09中的已审计XLSX哈希为43465a06f2ccf7c8b5bd2892bc7defb52f97487934fe93b16ae4c3936424676d。其价格可按0.001 GBP定点保存；原OOXML价格与该网格的最大差为7E-13 GBP。只在差值不超过1E-9 GBP时允许消除Excel表示尾差，保留原始表示与规范化记录，真实0.001不丢失。其他文件重新审计精度，不自动套用该阈值或尺度。聚合采用整数或Decimal；JSON以十进制字符串传递精确金额，前端显示和图表转换不能反过来作为计算真值。SQLite整数乘法与SUM前检查范围，防止溢出后静默转浮点。

主要行分类采用明确优先级，确保互斥并回合到总行数；质量标签允许重叠并单独统计。例如负单价、非C负数量、其他零值、有效正向、有效取消分别计数；不能把重叠的零价和非C负数量直接相加当排除总量。

POST、BANK CHARGES、M等代码在本文件真实存在；代码不符合数字格式不等于错误，也不能凭代码长度判断商品/费用。默认金额覆盖所有符合符号与字段条件的交易行，页面写明含费用等条目。StockCode分组先称“交易条目排名”；若进一步提供纯商品视图，先建立有证据、带版本的条目类型表，报告排除影响，并让参考计算采用相同口径。不要擅自将当前行金额标为商品GMV。

本快照有43张发票包含多个时间戳，但没有跨日或跨月发票。按原始交易行时间分期，并按InvoiceNo去重计数；不按InvoiceNo与时间戳组合增加订单数。新文件若出现跨期发票，先明确订单归期口径，并说明订单数可能不具备可加性；金额仍按行分期。
