## 1. 总体安排

两个题目与 FastAPI + Vue + SQLite + LangGraph 路线保留。最终页面和工具范围继续按 SPEC 完成，首轮先交付贯通前后端、真实数据和记录的一条小流程。`00_MASTER_PLAN.md` 与 SPEC 中的阶段是最终交付分类，不能理解为必须写完全部后端和所有页面才能验证第一次真实使用。本文件优先规定首轮施工顺序。

本项目优先完成真实电商数据导入、精确月度查询与可核验的页面。一个开发者同时只维护一个正在集成的主要功能，第二个 Codex 会话只改自己的项目。先复用约定和经验，不先建设两个项目共同依赖的通用平台或共享可变代码包。

本次方案审查已下载并审计 UCI 原始文件，结果见 `09_DATA_PREFLIGHT.md`。这证明审查环境能取得该版本数据，不能替代你的 Windows 环境安装、导入、模型接入或系统验收。获客尚未完成 12 家试验和人工标注。

## 2. 开工前的小范围检查

在用户实际选择的项目目录内读取适用 AGENTS.md、README、依赖和已有代码；不扫描其他磁盘找历史项目。已有代码先做增量评估，不能因为使用本方案而清空仓库。两个目录分别用独立 Git、虚拟环境、数据库和配置。若使用已建仓库，则沿用它的版本记录。

先实现最小 `doctor` 或等价脚本，实际输出操作系统、Python、Node、包管理器、Python 链接的 SQLite 版本、端口占用、模型配置是否存在（只输出存在与否）。先选与当前环境相容的具体版本，再固定锁文件。Windows/PowerShell 是默认说明环境；无需预先安装 Docker、重装 WSL 或新建云服务器。

使用 SQLite、单进程、单任务执行器和短事务起步。文件导入和模型请求在事务外执行。`10_RUNTIME_CONTRACT.md` 规定任务状态、checkpoint 和恢复规则。

研究与开发资料分开：只对开发集调试，人工 gold 不进入 Agent 可访问路径。用户可晚些补充学院任务书、模板和截止日期，但正式论文结构与研究结论须在相应阶段对齐。

## 3. 电商 E-S1：首先完成一条无需模型的真实查询

### 目标

在一个实际浏览器页面中，导入 UCI 原文件，选择历史月份，看到按固定口径计算的正向交易行金额、取消类金额、净交易金额和订单数，并能查到数据哈希、口径和排除记录。这是第一个可运行版本，不要求此时完成全部五个页面和八个工具。

### 实施顺序

1. 下载官方数据，记录原始 ZIP/XLSX 的哈希，复跑数据审计。哈希不同不能直接认定损坏，先查明版本差异。原始文件不可覆盖。
2. 冻结行分类与金额规范化规则。保留原始价格表示、规范化价格和处理原因。重复文件按哈希幂等，原文件中相同业务行默认保留。
3. 建立最少实体：数据快照、导入批次、交易行、质量问题、查询运行与结果。将主要排除类别设计为互斥分类，质量标签可以重叠，二者分别统计。
4. 首先实现 `get_dataset_profile`、`get_metric_definitions` 和按月指标查询；先支持一个明确指标与固定日期区间，再补其他指标。不能把“暂未支持”伪装成空结果。
5. 用独立脚本核对同一月份的金额与行数。官方原文件的审查结果可作为回归检查材料，最终参考实现必须与生产聚合函数独立。
6. 实现一个 Vue 页面：导入区域、日期/指标选择、结果表、数据口径与质量提示。连接真实 API，结果来自实际数据库。
7. 保存运行记录和浏览器验证证据，再继续下一个切片。

### 首轮验收

| 编号 | 用例 | 必须看到的结果 |
|---|---|---|
| E01 | 导入官方原文件 | 实际行数、来源、哈希和分类计数可查；分类能对账 |
| E02 | 再次导入相同字节 | 复用已有批次或明确提示重复，不使金额翻倍 |
| E03 | 查询 2011 年 9 月与 10 月各自指标 | 与独立计算逐项一致，精确值与显示值分开 |
| E04 | 价格 0.001 的真实记录 | 入库后不变成 0；原始值与规范化规则可追溯 |
| E05 | 选择数据外区间或不完整月份 | 明确无覆盖/部分覆盖，不自动换日期，不隐去提示 |
| E06 | 页面刷新、查询历史结果 | 结果仍可通过 ID 读取，不依赖浏览器内存 |

E-S1 通过状态只表示真实数据查询流程通过。模型和完整论文实验仍保持未完成。

## 4. 电商 E-S2：接入真实模型，再加入增强流程

先做实际模型能力冒烟：工具调用、结构化输出、错误响应、用量字段与超时处理；记录真实模型标识。缺 Key 时完成 E-S1、适配层、测试与页面配置入口，真实调用状态保留阻断。

B1 使用明确的基础多轮工具循环：模型提出工具调用 → 程序执行并返回结果/错误 → 模型继续或结束。它具备合理的工具描述、正常读取错误的能力、澄清输出、共同参数校验与预算，不限制成一次调用的弱基线。

B2 在相同工具、输入材料、输出结构和上限下加入显式任务条件检查、跨工具对账、报告主张核查及有限业务修复。两组均可由 LangGraph 承载，研究比较的是增强流程组合。SDK重试、结构化输出修复和图重试均通过同一个可审计预算入口。

先选少量开发任务走通：一个明确月份查询、一个缺少时间问题、一个利润/库存字段不支持问题、一个无匹配数据问题、一个可控工具错误问题。后两类测试若使用人为故障，标记为软件测试，不能混成真实经营记录。

报告关键数值采用结构化引用：模型给出 `claim_id`、`tool_call_id`、`field_path`、指标和期间；服务端解析引用并填入精确值和单位。B1/B2共用合法引用与输出格式检查。B2增加任务覆盖、期间可比、跨结果一致性和解释是否越界的核查。机械校验不能保证所有自然语言因果解释正确，未能自动判断的部分进入明确的人工抽查范围。

澄清验收必须有一次真正的“提问 → 暂停 → 补充条件 → 同一 run 恢复 → 得到结果”。它与正式实验中的首轮澄清题分开：主实验可以按原协议只评价首轮，但系统功能必须验证完整交互。

补做 `10_RUNTIME_CONTRACT.md` 中的暂停重启、重复恢复和历史只读检查。通过后再扩展期间比较、变化拆解、其余工具和完整五页面，最后建设正式任务集与实验。

## 7. 模型预算与进度

原正式计划的模型方案任务数为 `(100道题 + 120家企业) × 2方案 × 3重复 = 1320`。这是任务次数，每个任务可能消耗多个模型请求，还不含开发与试验。先分别用少量开发样本记录实际调用、Token、耗时和可核实费用，再按已授权额度估算正式运行；没有价格或用量时保持未知，不能记0。

首轮交付顺序是：环境和真实来源 → E-S1/L-S1 → E-S2/L-S2 → 其余功能 → 冻结和正式实验。6—8周继续只作为未核实的排期占位，不能当作承诺。

每完成一个切片更新 STATUS.json 与同步摘要、DECISIONS、EVIDENCE_INDEX、KNOWN_ISSUES、NEXT_SESSION。实际阶段可推进就继续；只有依赖缺失的部分标 BLOCKED。后续会话从已完成证据接着做，不重新创建项目。

## 8. 第一轮 Codex 应交付什么

电商交付：真实文件审计、冻结口径、幂等导入、一个月查询API和真实结果页面、独立对账、可运行说明、问题与状态记录；有模型配置时继续自然语言查询与澄清恢复。

代码、文档和验收记录都必须来自实际执行。不能以功能列表、空目录或预写的实验结果替代上述产物。
